# Estrutura dos módulos

## Escopo atual

O Ouroboros é uma fintech fictícia e educacional organizada como monólito modular: dois hosts ASP.NET Core, a API externa e o backoffice, compõem os módulos e são a entrada HTTP da aplicação ([Hosts](hosts.md)). Nesta etapa existe a estrutura dos projetos e, no Identity, a entidade `User` com o hash de senha ([Domínio de identidade](identity.md)), a criação do primeiro administrador ([Criar o primeiro administrador](../identity/first-admin.md)) o login com sessões e refresh token ([Fazer login com e-mail e senha](../identity/login.md)), a renovação do access token com rotação do refresh token ([Renovar o access token](../identity/refresh-session.md)), o logout da sessão atual ([Encerrar a sessão atual](../identity/logout.md)), o logout de todas as sessões ([Encerrar todas as sessões](../identity/logout-all.md)), a consulta do próprio usuário ([Consultar o próprio usuário](../identity/me.md)), o cadastro de cliente por e-mail, com a solicitação e a conclusão ([Cadastrar cliente por e-mail](../identity/registration.md)), a solicitação de redefinição de senha ([Redefinir a senha por e-mail](../identity/password-reset.md)) e o limite de requisições por IP dos endpoints de autenticação ([Limitar requisições](../identity/auth-rate-limiting.md)) e, no Settings, os parâmetros do sistema com histórico ([Parâmetros do sistema](system-parameters.md)); os demais modelos de domínio e casos de uso ainda serão definidos.

A [solution Ouroboros.slnx](../../Ouroboros.slnx) reúne onze projetos C# independentes:

| Projeto | Papel |
| --- | --- |
| `Ouroboros.Api` | Host da API externa (app do cliente, anônimos e integrações) e composition root: referencia e registra os cinco módulos e declara os controllers da API externa em `Controllers/<Module>/`. |
| `Ouroboros.Backoffice.Api` | Host interno do backoffice: referencia e registra os cinco módulos, declara os controllers do backoffice em `Controllers/<Module>/` e roda comandos de operação em `CommandLine/` (hoje, o `create-admin`). |
| `Ouroboros.Hosting` | Configuração HTTP comum aos dois hosts (controllers, versionamento, ProblemDetails, política padrão de autorização por público e o middleware de limite de requisições); não referencia módulos. |
| `Ouroboros.BuildingBlocks` | Código técnico compartilhado pelos módulos: a base `Entity` e os tipos de persistência das [convenções das entidades](entity-conventions.md); não referencia módulos nem hosts ([BuildingBlocks](building-blocks.md)). |
| `Ouroboros.Modules.Identity` | Identidade: entidade `User`, hash e política de senha, criação do primeiro administrador, login com sessões e refresh token, renovação do access token com rotação do refresh token, logout da sessão atual e de todas as sessões, consulta do próprio usuário, cadastro de cliente por e-mail (solicitação e conclusão), solicitação de redefinição de senha, limite de requisições por IP da autenticação, emissão e validação dos tokens JWT, porta de envio de e-mail e persistência no schema `identity`; referencia o Settings, só pelos `Contracts`. |
| `Ouroboros.Modules.Settings` | Parâmetros do sistema: contrato de leitura `ISystemParameters`, validação dos valores e histórico de alterações no schema `settings` ([Parâmetros do sistema](system-parameters.md)). |
| `Ouroboros.Modules.Customers` | Estrutura reservada para clientes. |
| `Ouroboros.Modules.Accounts` | Estrutura reservada para contas. |
| `Ouroboros.Modules.Transactions` | Estrutura reservada para transações. |
| `Ouroboros.ArchitectureTests` | Testes de arquitetura da visibilidade dos módulos, da não exposição do `Id` interno das entidades, das dependências de `Ouroboros.BuildingBlocks` e da descoberta, das rotas e do versionamento dos controllers, na pasta `tests`. |
| `Ouroboros.IntegrationTests` | Testes de integração da API contra um PostgreSQL real em container, na pasta `tests`; exigem Docker (veja [Testes de integração](integration-tests.md)). |

Cada módulo tem seu próprio `.csproj` e pode ser compilado individualmente. As pastas `src`, `Modules` e `tests` apenas organizam os projetos na solution. Dentro de cada módulo, as pastas abaixo são divisões lógicas de uma única class library, sem isolamento de compilação entre elas.

## Padrão para novos módulos

Um pedido de criação de módulo produz apenas esta estrutura, seguindo a nomenclatura existente:

```text
Ouroboros.Modules.<Module>/
├── Application/
├── Contracts/
├── Domain/
├── Infrastructure/
├── DependencyInjection.cs
└── Ouroboros.Modules.<Module>.csproj
```

| Pasta ou arquivo | Responsabilidade reservada |
| --- | --- |
| `Application` | Implementações `internal` dos casos de uso, em `Application/<Funcionalidade>/`, quando solicitados. |
| `Contracts` | Fronteira pública do módulo: interfaces dos casos de uso expostos, com request e response, em `Contracts/<Funcionalidade>/`; nomes das políticas por capacidade; contratos mínimos para outros módulos, quando necessários. |
| `Domain` | Entidades, objetos de valor e regras do domínio, após sua definição; as entidades seguem as [convenções de identificadores e datas](entity-conventions.md). |
| `Infrastructure` | Persistência e outras implementações de infraestrutura, quando solicitadas; o DbContext e as migrations ficam em `Infrastructure/Persistence`, conforme [Persistência](persistence.md#padrão-para-um-módulo-novo). |
| `DependencyInjection.cs` | Ponto de registro das dependências do módulo. |

As pastas vazias são preservadas no Git por arquivos `.gitkeep`, e itens `Folder` nos projetos explicitam sua organização no Visual Studio. Hoje o Identity e o Settings têm conteúdo. O Identity, descrito em [Domínio de identidade](identity.md):

- `Domain`: em `Users/`, a entidade `User`, que herda a base `Entity` de [BuildingBlocks](building-blocks.md), o enum `UserRole` e a regra estrita de e-mail `EmailAddresses` ([Cadastrar cliente por e-mail](../identity/registration.md#regra-estrita-de-e-mail)); em `Sessions/`, as entidades `Session` e `RefreshToken` ([Fazer login com e-mail e senha](../identity/login.md#persistência)); em `EmailTokens/`, a entidade `EmailToken`, com as fábricas `ForRegistration` e `ForPasswordReset`, e o enum `EmailTokenPurpose` ([Cadastrar cliente por e-mail](../identity/registration.md#persistência));
- `Application`: em `Security/`, a porta `IPasswordHasher`, o `UserPasswordVerifier`, a `PasswordPolicy`, a lista `common-passwords.txt`, embutida como recurso ([Política de senha](password-policy.md)), e o `OpaqueTokens` (chamado `RefreshTokens` até a #20), que gera tokens opacos (refresh token e tokens enviados por e-mail) e calcula seu SHA-256; em `Notifications/`, a porta `IEmailSender` e o `EmailMessage` ([Envio de e-mail](email.md)); em `Administrators/`, o caso de uso `CreateFirstAdmin` ([Criar o primeiro administrador](../identity/first-admin.md)); em `Sessions/`, os casos de uso `Login` ([Fazer login com e-mail e senha](../identity/login.md)), `RefreshSession` ([Renovar o access token](../identity/refresh-session.md)), `Logout` ([Encerrar a sessão atual](../identity/logout.md)) e `LogoutAll` ([Encerrar todas as sessões](../identity/logout-all.md)), o `LoginChannels`, que mapeia cada canal ao papel aceito, e o `AccountLockout`, com o registro `LockoutPolicy` ([Bloquear a conta](../identity/account-lockout.md)); em `Users/`, o caso de uso `GetCurrentUser` ([Consultar o próprio usuário](../identity/me.md)); em `Registrations/`, os casos de uso `RequestRegistration` e `CompleteRegistration` ([Cadastrar cliente por e-mail](../identity/registration.md)); em `PasswordResets/`, o caso de uso `RequestPasswordReset` ([Redefinir a senha por e-mail](../identity/password-reset.md));
- `Infrastructure`: em `Persistence/`, o `IdentityDbContext`, suas options, o `PersistenceErrors`, que reconhece a violação de unicidade do PostgreSQL para que `Application` não dependa do Npgsql ([Concluir o cadastro](../identity/registration.md#regras-da-conclusão)), as migrations (`InitialCreate`, `AddUsers`, `AddSessions`, `AddAccountLockout`, `AddRefreshTokenRevocation` e `AddEmailTokens`) e, em `Configurations/`, a `UserConfiguration`, a `SessionConfiguration` (com a `RefreshTokenConfiguration` no mesmo arquivo) e a `EmailTokenConfiguration`; em `Security/`, o `AspNetCorePasswordHasher` e os tipos dos [tokens JWT](authentication.md) (`AccessTokenIssuer`, `JwtOptions` e `JwtOptionsValidator`); em `Email/`, os adaptadores `PickupDirectoryEmailSender` e `UnconfiguredEmailSender`, com `EmailOptions`, `EmailOptionsValidator` e o enum `EmailProvider`; em `RateLimiting/`, o `AuthRateLimiting`, que registra o rate limiter, e `AuthRateLimitOptions`, `FixedWindowPolicy` e `AuthRateLimitOptionsValidator` ([Limitar requisições](../identity/auth-rate-limiting.md#implementação));
- `Contracts`: os nomes das políticas por capacidade em `IdentityPolicies`, os das políticas de limite de requisições em `IdentityRateLimitPolicies` e os dos claims do access token em `IdentityClaims` (`sub`, `role`, `sid`), que saiu de `Infrastructure/Security` na #18 para os controllers lerem o usuário autenticado; em `Administrators/`, o caso de uso `ICreateFirstAdmin` com `CreateFirstAdminRequest`, `CreateFirstAdminResult` e `CreateFirstAdminOutcome`; em `Sessions/`, o caso de uso `ILogin` com `LoginRequest`, `LoginChannel`, `LoginResult` e `SessionTokens`, o `IRefreshSession` com `RefreshSessionRequest` e `RefreshSessionResult`, o `ILogout` com `LogoutRequest` e `LogoutResult` e o `ILogoutAll` com `LogoutAllRequest`; em `Users/`, o caso de uso `IGetCurrentUser` com `GetCurrentUserRequest` e `CurrentUser`; em `Registrations/`, o caso de uso `IRequestRegistration` com `RequestRegistrationRequest` e `RequestRegistrationResult` e o `ICompleteRegistration` com `CompleteRegistrationRequest`, `CompleteRegistrationResult` e `CompleteRegistrationOutcome`; em `PasswordResets/`, o caso de uso `IRequestPasswordReset` com `RequestPasswordResetRequest` e `RequestPasswordResetResult`.

O Settings, descrito em [Parâmetros do sistema](system-parameters.md):

- `Domain`: em `Parameters/`, as entidades `Parameter` e `ParameterHistory`, o enum `ParameterDataType` e as regras `ParameterValueRules`;
- `Application`: em `Parameters/`, a implementação `SystemParameters` do contrato de leitura e o `ParameterWriter`, que grava parâmetro e histórico na mesma transação;
- `Infrastructure`: em `Persistence/`, o `SettingsDbContext`, suas options, as migrations `InitialCreate` (tabelas e valores iniciais), `AddLockoutParameters` (parâmetros do bloqueio de conta) e `AddRegistrationParameters` (parâmetros da solicitação de cadastro) e `AddPasswordResetParameters` (parâmetros da solicitação de redefinição de senha) e as configurações `ParameterConfiguration` e `ParameterHistoryConfiguration` (em `Configurations/`);
- `Contracts`: o contrato `ISystemParameters` e a `ParameterNotFoundException`.

`Contracts` continua vazia nos demais módulos. Nenhum módulo tem pasta `Controllers`: os controllers ficam nos hosts ([Controllers HTTP nos hosts](http-controllers.md)).

Os métodos `AddIdentityModule`, `AddSettingsModule`, `AddCustomersModule`, `AddAccountsModule` e `AddTransactionsModule` retornam `IServiceCollection`, e cada host os invoca no próprio `Program.cs` ([API externa](../../src/Ouroboros.Api/Program.cs) e [backoffice](../../src/Ouroboros.Backoffice.Api/Program.cs)). Só os do Identity e do Settings registram algo. O do Identity registra a autenticação JwtBearer com as opções `Authentication:Jwt` validadas na subida, o `AccessTokenIssuer` e as políticas por capacidade ([Autenticação](authentication.md)), as opções `Identity:Email` validadas na subida, os adaptadores de e-mail e o `IEmailSender` conforme o provedor configurado ([Envio de e-mail](email.md)), as opções `Identity:RateLimiting` validadas na subida e o rate limiter com uma política por IP para cada política configurada ([Limitar requisições](../identity/auth-rate-limiting.md)), o `IPasswordHasher` (implementado por `AspNetCorePasswordHasher`) e o `UserPasswordVerifier` como singletons, o `ICreateFirstAdmin`, o `ILogin`, o `IRefreshSession`, o `ILogout`, o `ILogoutAll`, o `IGetCurrentUser`, o `IRequestRegistration`, o `ICompleteRegistration`, o `IRequestPasswordReset` e o `AccountLockout` como scoped, o `TimeProvider` e o `AuditTimestampsInterceptor` (os dois com `TryAddSingleton`) e o `IdentityDbContext`, com a connection string validada na subida (veja [Persistência](persistence.md)). O do Settings registra as próprias options de banco validadas na subida, o `TimeProvider` e o `AuditTimestampsInterceptor` (também com `TryAddSingleton`, então o primeiro registro vale para os dois módulos), o `SettingsDbContext`, o `ISystemParameters` e o `ParameterWriter`. Nenhum módulo cria o banco nem aplica migrations ao subir.

Um módulo não declara controllers nem registra application part. Para ganhar endpoints, ele expõe cada caso de uso como interface `public` em `Contracts/<Funcionalidade>/`, implementa-o `internal` em `Application/<Funcionalidade>/` e registra o par em `Add<Module>Module`; o controller é declarado no host, conforme [Como criar um endpoint](http-controllers.md#como-criar-um-endpoint). Hoje os casos de uso expostos aos hosts são os do Identity: o `ILogin`, o `IRefreshSession`, o `ILogout` e o `ILogoutAll`, chamados pelos `SessionsController` dos dois hosts, o `IGetCurrentUser`, chamado pelos `MeController`, o `IRequestRegistration` e o `ICompleteRegistration`, chamados pelo `RegistrationsController` da API externa, o `IRequestPasswordReset`, chamado pelo `PasswordResetsController` da API externa, e o `ICreateFirstAdmin`, chamado pelo comando `create-admin` do backoffice, não por um controller; o único contrato usado por outro módulo é o `ISystemParameters` do Settings.

Entidades, DTOs, handlers, repositórios, DbContexts, migrations, endpoints e dados de exemplo só serão adicionados mediante solicitação de funcionalidades; o DbContext e a migration inicial vazia do Identity vieram da configuração da persistência (#5), a base `Entity` e os tipos de persistência que a acompanham, das convenções das entidades (#6), o `User`, o hash de senha e a migration `AddUsers`, do domínio de identidade (#8), o módulo Settings, dos parâmetros do sistema (#33), a política de senha e o caso de uso do primeiro administrador, da #11, e as sessões, o refresh token, o caso de uso `ILogin`, a migration `AddSessions` e os primeiros controllers, do login (#12), o bloqueio de conta, com as migrations `AddAccountLockout` e `AddLockoutParameters`, da #13, o limite de requisições por IP, da #14, o caso de uso `IRefreshSession`, a migration `AddRefreshTokenRevocation` e as rotas de renovação, da #15, o caso de uso `ILogout` e as rotas de logout, da #17, e o caso de uso `ILogoutAll`, as rotas de logout-all e o `IdentityClaims` em `Contracts`, da #18, o caso de uso `IGetCurrentUser` e as rotas `me`, da #19, a entidade `EmailToken`, a migration `AddEmailTokens`, o caso de uso `IRequestRegistration`, a rota de cadastro e a migration `AddRegistrationParameters`, da #20, e o caso de uso `ICompleteRegistration`, o `PersistenceErrors` e a rota de conclusão do cadastro, da #21, e o caso de uso `IRequestPasswordReset`, a rota de solicitação de redefinição de senha e a migration `AddPasswordResetParameters`, da #22. Criar um módulo não autoriza inferir seus casos de uso.

Na estrutura inicial não havia `BuildingBlocks`, porque nenhum mecanismo transversal era necessário, e a base `Entity` nasceu no Identity (#6). Quando o Settings, segundo módulo com entidades, precisou dela, a base e os tipos de persistência foram extraídos para `Ouroboros.BuildingBlocks` (#33), conforme [Código compartilhado entre módulos](building-blocks.md). BuildingBlocks só guarda código técnico usado por mais de um módulo, nunca regras de negócio.

## Visibilidade dos tipos

Todo tipo de um módulo é `internal` por padrão. Somente dois pontos são `public`:

- a classe `DependencyInjection` e seu método `Add<Module>Module`, usados pelo host;
- os tipos em `Contracts` e seus sub-namespaces, que formam a fronteira pública do módulo para os hosts e os demais módulos: interfaces dos casos de uso, seus request e response (só com `ExternalId`, nunca entidades) e constantes como os nomes das políticas e dos claims do access token.

Entidades, objetos de valor, implementações dos casos de uso, repositórios e DbContexts das pastas `Domain`, `Application` e `Infrastructure` nunca são `public`, e módulos não declaram controllers. A única exceção são as classes de migration geradas pelo `dotnet ef`, explicada em [Migrations geradas](persistence.md#migrations-geradas). Assim, os hosts e qualquer módulo que referencie outro só enxergam `Contracts`: um controller que injete um tipo interno não compila (CS0122). Tornar um tipo `public` fora dessas exceções exige mover o tipo para `Contracts` ou registrar a decisão nesta nota. O [teste de arquitetura](http-controllers.md#testes-de-arquitetura) falha se um módulo expuser outro tipo `public` (exceto migrations) ou conceder `InternalsVisibleTo` a `Ouroboros.Api` ou a `Ouroboros.Backoffice.Api`.

Quando um projeto de teste precisa de tipos internos, o acesso é concedido com `InternalsVisibleTo` no `.csproj` do módulo, nunca aos hosts, e não tornando tipos públicos. Hoje o Identity e o Settings o concedem a `Ouroboros.IntegrationTests`: no Identity, para que os testes das [convenções das entidades](entity-conventions.md#testes) usem o `IdentityDbContext`, os do [domínio de identidade](identity.md#testes) usem `User`, o hasher e o verificador, os do [e-mail](email.md#testes) usem a porta e os adaptadores, e os do [login](../identity/login.md#como-verificar) usem o `User`, o hasher e o `IdentityDbContext`; no Settings, para que os [testes dos parâmetros](system-parameters.md#testes) usem as entidades, o `SettingsDbContext` e o `ParameterWriter`. Os tipos de [BuildingBlocks](building-blocks.md) são `public` e não dependem disso. A descoberta dos DbContexts para aplicar migrations não depende disso: eles são resolvidos pela DI, com os tipos encontrados por reflexão.

O `Id` (`long`) das entidades também não sai do módulo: `Contracts`, rotas e DTOs de resposta (com nome terminado em `Response`) usam o `ExternalId`, conforme [Identificadores, datas e nomes das entidades](entity-conventions.md); um teste de arquitetura verifica essa regra por convenção de nomes.

## Pacotes NuGet

As versões dos pacotes são centralizadas em [Directory.Packages.props](../../Directory.Packages.props) (Central Package Management). Os `.csproj` declaram apenas `<PackageReference Include="..." />`, sem `Version`. Para adicionar ou atualizar um pacote, altere seu `PackageVersion` nesse arquivo.

## Fronteiras adotadas para a evolução

As decisões abaixo orientam a evolução dos módulos. A base de persistência já existe; as demais regras ainda não têm controles automáticos:

- Cada módulo é dono de seus dados e mapeamentos. Todos usam um único banco PostgreSQL, com os schemas `identity`, `settings`, `customers`, `accounts` e `transactions` e um DbContext e histórico de migrations próprios por módulo, conforme [Persistência](persistence.md). Hoje existem os schemas `identity`, com as tabelas `users`, `sessions`, `refresh_tokens` e `email_tokens`, e `settings`, com as tabelas `parameters` e `parameter_history`; as entidades seguem as [convenções das entidades](entity-conventions.md).
- JOINs, SQL direto e foreign keys entre schemas de módulos diferentes são proibidos. A aplicação deverá obter dados de outro módulo por contratos públicos pequenos e chamadas em memória.
- Entidades de domínio e entidades EF não serão compartilhadas entre módulos; o que é compartilhado é só a base técnica de [BuildingBlocks](building-blocks.md), que não referencia módulos nem hosts.
- Um módulo pode referenciar o projeto de outro apenas para usar os tipos de `Contracts` dele. As referências entre módulos são unidirecionais, sem ciclos. O Settings não depende de nenhum módulo; os outros módulos leem parâmetros pelo `ISystemParameters` ([Parâmetros do sistema](system-parameters.md)). A primeira dependência entre módulos veio na [#11](https://github.com/adnerscarpelini/ouroboros-server/issues/11): o `.csproj` do Identity referencia o projeto do Settings, e o Identity usa só o `ISystemParameters` e a `ParameterNotFoundException` de `Settings.Contracts`, para ler o domínio aceito na [criação do primeiro administrador](../identity/first-admin.md), desde a #13, os parâmetros do [bloqueio de conta](../identity/account-lockout.md#configuração) desde a #20, os da [solicitação de cadastro](../identity/registration.md#configuração) e, desde a #22, os da [solicitação de redefinição de senha](../identity/password-reset.md#configuração). É a única referência entre módulos. O futuro módulo Customers vai se vincular ao usuário do Identity pelo `ExternalId` (o claim `sub` do access token), sem referência entre os projetos, sem foreign key entre schemas e sem transação conjunta com a criação do usuário ([Vínculo futuro com o Customers](../identity/registration.md#vínculo-futuro-com-o-customers)); o Settings não pode referenciar o Identity, o que criaria um ciclo. Os tipos internos do Settings continuam inacessíveis ao Identity; ainda não há teste de arquitetura que verifique a direção das referências entre módulos.
- Transações locais serão o padrão. Operações futuras em vários módulos exigirão uma decisão explícita de consistência e coordenação; DbContexts diferentes não garantem atomicidade conjunta.
- Os hosts ficarão responsáveis por HTTP e composição, enquanto regras de negócio pertencerão aos módulos. Casos de uso poderão seguir Vertical Slices sem criar subprojetos por camada.

Essas fronteiras são escolhas do Ouroboros. Pastas e convenções, por si sós, não impedem violações em runtime. Hoje só a visibilidade dos tipos, a não exposição do `Id` interno em `Contracts` e respostas, a ausência de referências de BuildingBlocks a módulos e hosts, o mapeamento de cada DbContext só no schema do próprio módulo, as convenções de identificadores, datas e nomes das entidades, as rotas e versões dos controllers, a exigência da connection string, da chave de assinatura dos tokens e das políticas de limite de requisições na subida, a recusa do adaptador de e-mail local fora de `Development`, a autenticação e a autorização dos hosts e a aplicação das migrations dos módulos num PostgreSQL real são verificadas automaticamente; testes para as demais fronteiras e inspeções de mapeamentos deverão acompanhar a implementação que vier a necessitá-los.

## Execução e limites

Consulte o [README](../../README.md) para abrir a solution no Visual Studio, compilar a solução ou um módulo, [executar os testes](../../README.md#testes) e iniciar os hosts.

Cada host exige a connection string `ConnectionStrings:Ouroboros`, a chave `Authentication:Jwt:SigningKey` e políticas válidas em `Identity:RateLimiting` e não sobe sem elas, nem com o adaptador de e-mail local fora de `Development`; o README explica como [subir o PostgreSQL local com Docker Compose e aplicar as migrations](../../README.md#banco-de-dados-local) e como [configurar a chave](../../README.md#chave-de-assinatura-dos-tokens). Cada host mapeia os controllers do próprio projeto; hoje cada um tem o `SessionsController`, com o login, a renovação e o logout, anônimos e limitados por IP, e o logout-all, que exige access token, e o `MeController`, com a consulta do próprio usuário, que também exige access token; só a API externa tem o `RegistrationsController`, com a solicitação e a conclusão do cadastro, e o `PasswordResetsController`, com a solicitação de redefinição de senha, anônimas e limitadas por IP; as demais rotas respondem 401 sem token e 404 com token válido. Há testes de arquitetura e [testes de integração contra um PostgreSQL real](integration-tests.md), que exercitam o login, a renovação, o logout, o logout-all e a consulta do próprio usuário nos dois hosts, a solicitação e a conclusão do cadastro e a solicitação de redefinição de senha na API externa e o caso de uso do primeiro administrador. O Identity tem o usuário, o hash e a política de senha, a emissão e validação de access tokens ([Autenticação](authentication.md)), a criação do primeiro administrador por comando de linha ([Criar o primeiro administrador](../identity/first-admin.md)), o login com e-mail e senha, que abre uma sessão e emite access token e refresh token ([Fazer login com e-mail e senha](../identity/login.md)), o bloqueio da conta após falhas seguidas de senha ([Bloquear a conta](../identity/account-lockout.md)), a renovação do access token com rotação do refresh token e detecção de reuso ([Renovar o access token](../identity/refresh-session.md)), o logout da sessão atual ([Encerrar a sessão atual](../identity/logout.md)), o logout de todas as sessões ([Encerrar todas as sessões](../identity/logout-all.md)), a consulta do próprio usuário ([Consultar o próprio usuário](../identity/me.md)), o cadastro de cliente por e-mail, da solicitação à criação do `Customer` ([Cadastrar cliente por e-mail](../identity/registration.md)), a solicitação de redefinição de senha de clientes ([Redefinir a senha por e-mail](../identity/password-reset.md)) e o limite de requisições por IP dos endpoints anônimos ([Limitar requisições](../identity/auth-rate-limiting.md)). Não há CI nem operações financeiras nesta etapa. Ledger permanece fora do escopo.

O QA da estrutura inicial verificou a compilação da solution e dos quatro módulos individualmente, sem warnings ou erros, além da inicialização do host, que na época não exigia connection string (exigência introduzida na #5). A interface do Visual Studio não foi inspecionada; a validação usou os arquivos de projeto e a CLI. Não há comportamento de domínio a validar nesta entrega.
